## Что должно заработать

Слепая приёмка нашла две поломки в упаковке и один недоделанный провод.

**1. `docker build` падает.** `error: package directory 'userbot' does not exist` — `Dockerfile` копирует в образ только часть пакетов (`matcher/`, `store/`) и сразу запускает `pip install --no-cache-dir .`, а `pyproject.toml` перечисляет пакеты `userbot`/`worker`/`panel`, которых ещё нет в образе на этом шаге. Почини порядок: либо копируй весь исходник (`COPY . .`) до `pip install .`, либо — проще и быстрее для пересборки при правках кода — не устанавливай локальные пакеты как дистрибутив вообще: поставь только внешние зависимости (`pip install telethon aiogram aiosqlite aiohttp tzdata` — версии смотри в `pyproject.toml`), скопируй исходники, и запускай `python -m userbot.main`/`python -m panel.main` прямо из рабочей директории (Python находит локальные пакеты через `cwd` на `sys.path`, установка не нужна). Собери образ (`docker build -t tg-lead-catcher .`) и подтверди, что он реально собирается до конца.

**2. `pip install -e .` падает.** `ModuleNotFoundError: No module named 'telethon'` при сборке. Причина: `setuptools` при PEP 517-сборке видит в корне файл `setup.py` (это мастер настройки бота из брифа, не имеет отношения к упаковке) и пытается исполнить его как legacy build-скрипт в изолированном окружении сборки, где ещё нет зависимостей проекта — сам мастер на верхнем уровне импортирует `telethon`. Это конфликт имён: `setup.py` — зарезервированное имя в инструментах упаковки Python.

Исправление: переименуй мастер настройки в `configure.py` (или другое имя, не конфликтующее с setuptools — не `setup.py`). Обнови все места, которые его запускают или упоминают: `docker-compose.yml`/`deploy/*` (если ссылаются), `README`/`CLAUDE.md` между маркерами Autopilot (команда установки), тесты (`tests/test_setup.py` — переименуй в `tests/test_configure.py` для симметрии, если не жалко переименовать; если жалко — оставь имя файла, просто поправь то, что импортирует модуль `setup` → `configure`). Убедись, что после переименования `pip install -e ".[dev]"` (или как у вас называется dev-экстра) реально проходит успешно.

**3. `TZ` из `.env` никуда не доходит.** Мастер настройки пишет `TZ` в `.env`, но ни один рантайм-процесс (`userbot/main.py`, `panel/main.py`, `worker/runner.py`) не читает `os.environ["TZ"]` и не переносит его в `settings.tz` — карточка доставки всегда использует сид-значение `Europe/Moscow` из схемы, а не то, что реально в `.env`. Почини: при старте `userbot/main.py` (там, где уже читаются другие переменные окружения для сборки клиента) — если `TZ` задан в окружении и отличается от текущего `settings.tz`, обнови `settings.tz` через `SettingsRepo.update` один раз при старте.

Прогони `python -m pytest` после переименования — обнови импорты, которые ссылаются на старое имя модуля. Не меньше 146 passed (число тестов может измениться из-за переименования файла, это нормально).
