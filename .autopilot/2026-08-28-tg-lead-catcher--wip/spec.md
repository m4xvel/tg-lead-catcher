# Спецификация: tg-lead-catcher

## Задача

Пользователь ищет клиентов в Telegram: люди пишут о своей проблеме в открытых и
закрытых чатах, где он уже состоит, и это — готовые лиды. Вручную читать десятки
чатов в поиске нужных слов нереально: сообщения тонут в потоке, а пока их найдёшь
вручную, лид уже нашёл кого-то другого. Нужен способ автоматически ловить такие
сообщения по ключевым словам и сразу видеть, кто их написал и как с ним связаться —
без найма модератора и без обращения к разработчику каждый раз, когда список чатов
или слов меняется.

## Решение

Программа работает от основного Telegram-аккаунта пользователя (userbot) и молча
следит за выбранными чатами. Как только в тексте или подписи к медиа встречается
нужное слово, фраза или совпадение по регулярке — и рядом нет минус-слова — сообщение
целиком улетает в выбранный чат-приёмник (или в «Избранное»), а следом отдельным
сообщением приходит карточка с автором, ссылкой на оригинал и тем, по какому ключу
сработало. Всё управление — добавление и удаление чатов-источников, чатов-приёмников
и ключевых слов, пауза, статистика, проверка ключа на тестовом тексте — идёт кнопками
внутри отдельного Telegram-бота, полностью на русском. Ничего не редактируется руками
в файлах. Первый запуск проводит мастер `setup`, который сам всё спрашивает и
проверяет; секреты пользователь получает и хранит сам.

## Решения по реализации

### 1. Стек и структура репозитория

Python 3.11+, Telethon (userbot), aiogram 3 (панель), SQLite (`aiosqlite` для
неблокирующего доступа из обоих процессов). Один репозиторий, один Docker-образ,
два процесса в `docker compose` (`userbot`, `panel`) плюс общая база — так `panel`
не блокирует `userbot` во время долгих операций (скан истории). Локальный запуск
без Docker — те же два процесса через `Планировщик Windows` (R65).

- `matcher/` — чистая логика сопоставления, без Telegram-зависимостей: тестируется
  без сети и без БД.
- `store/` — единственная точка доступа к SQLite: схема, миграции, репозитории.
- `userbot/` — Telethon-клиент: слушает события, гоняет `matcher`, кладёт совпадения
  в очередь `store`, исполняет доставку.
- `panel/` — aiogram-бот: меню, FSM мастеров ввода, чтение/запись через `store`.
- `worker/` — обработчик очереди доставки: ретраи, глобальный лимит, живёт внутри
  процесса `userbot` (он единственный, кто может форвардить).
- `setup.py` — интерактивный мастер (R56), отдельный вход, не часть рантайма.

Репозиторий живёт в `C:\Users\X79\leed`, инициализирован `git init` в самом начале
сборки, до первого файла кода (R12) — сделано в Phase 0 автопилота.

### 2. Схема данных (SQLite, `./data/bot.db`)

```
sources(id, chat_id UNIQUE, title, kind[group|supergroup|channel|private],
        paused BOOL, last_processed_msg_id, added_at)
receivers(id, chat_id UNIQUE, title, added_at)
keywords(id, kind[word|phrase|regex], pattern, is_stop BOOL, created_at)
settings(key PRIMARY KEY, value)                 -- окна, лимиты, ретеншн, шаблон, tz
                                                  -- tz по умолчанию "Europe/Moscow",
                                                  -- переопределяется переменной TZ в .env
                                                  -- при первом запуске мастера (R14)
hits(id, source_chat_id, message_id, author_id, author_username, author_name,
     matched_keywords, text_hash, text_preview[500], created_at)
delivery_queue(id, hit_id, receiver_chat_id, status[pending|sent|failed],
                attempts, next_attempt_at, error)
```

`hits` покрывает R25.1/R32 (дедуп по id — уникальный индекс на
`(source_chat_id, message_id)`), R33 (дедуп по автору+хешу текста за окно —
индекс на `(author_id, text_hash, created_at)`), R67 (лог), R68 (ретеншн —
плановая чистка по `created_at`). `delivery_queue` покрывает R43/R61 (задача на
доставку — на каждого приёмника отдельно) и R62 (лимит читает `status=sent` за
последнюю минуту).

### 3. Матчинг ключевых слов (R17–R21)

Каждый `keywords.kind` компилируется в один `re.Pattern` при загрузке и при
изменении списка:

- `word` → `\b<escaped>\w*` с учётом словоформ (ловит хвост слова, не начало
  внутри другого) — реализует R17 без морфологии, как решено брифом (R72).
- `phrase` → экранированная фраза как есть.
- `regex` (`re:`) → компилируется как есть; `re.error` на добавление отклоняется
  с текстом ошибки, ключ не сохраняется (R19.1).

Перед компиляцией текст и паттерн приводятся к нижнему регистру и `ё`→`е`
(R20). Ключ считается сработавшим, если хотя бы один `word/phrase/regex`
совпал и ни один `is_stop` не совпал (R21).

### 4. Приём и обработка сообщений (userbot)

Обработчики Telethon на `NewMessage` и `MessageEdited`, оба гоняют одну и ту же
функцию `process(event)`:

1. Отсечь: свой аккаунт, боты, чат-приёмник (R34); чат не в `sources` или
   `paused` — выйти.
2. Взять текст + подписи медиа (R22), прогнать через `matcher`.
3. Не сработало → выйти. Сработало → проверить дедуп по id (R32) и по
   автору+тексту за окно (R33); если это дубль по автору — обновить «также
   в: …» у исходной записи и выйти без новой доставки.
4. Записать `hits`, поставить по одной записи `delivery_queue` на каждый
   активный приёмник (R16, R43).
5. Обновить `sources.last_processed_msg_id` этого чата.

Альбомы (`grouped_id`) буферизуются короткое окно и обрабатываются одной
доставкой (R24).

### 5. Доставка (worker, R27–R31, R43, R61–R62)

Отдельный цикл читает `delivery_queue` по `status=pending`, отправляет не
быстрее глобального лимита (`settings.rate_limit`, по умолчанию 20/мин, R62):

- Форвард; на `ChatForwardsRestrictedError` — копия текста тем же сообщением
  (R27).
- Следом — карточка по шаблону из `settings.card_template` (R28, R31),
  с `tg://user?id=` при отсутствии username (R29) и корректной ссылкой на
  оригинал (R30).
- Ошибка → `attempts += 1`, экспоненциальная задержка, после 3 попыток —
  `status=failed` + уведомление владельцу (R43, R61). `FloodWaitError` —
  отдельная ветка: не тратит попытку, ждёт указанное время, пишет в лог (R63).
- Недоступный чат-приёмник или источник (кикнули, удалили) — при следующей же
  ошибке доставки/чтения помечается неактивным (`paused` для источника,
  уведомление для приёмника) — R43, R76i.

### 6. История и догон (R35–R37)

При старте, для каждого активного источника: если `last_processed_msg_id`
задан — дочитать сообщения новее него (без верхнего предохранителя — это
именно пропущенное за время простоя, R35/R54, отличие от ручного скана ниже).
Кнопка «Просканировать 7 дней» и снятие индивидуальной паузы (R78i) используют
общую функцию `catch_up`, но с предохранителем: не глубже `settings.scan_days`
(по умолчанию 3, а для ручной кнопки — до 7 по явному запросу пользователя),
не больше 500 сообщений, с паузой между запросами Telethon (R37).

### 7. Панель (aiogram, R38–R55)

FSM-мастера на добавление источника/приёмника (три способа, R38–R40, R40.1);
списки с пагинацией и inline-кнопками удаления/паузы (R41, R42); построчный
парсер ввода ключей с отсечением дублей (R44–R46); `/check` через `matcher`
без сохранения (R47); тумблер мониторинга — глобальный флаг в `settings`,
проверяемый в п.4 шаг 1 (R48); экраны статуса/статистики/топа/истории —
агрегирующие запросы к `hits`/`delivery_queue` (R49–R52); диалог догона при
снятии глобальной паузы — сравнение времени снятия с временем последней
установки паузы (R53); `/export` — дамп `sources/keywords/receivers` в JSON
(R55).

### 8. Настройка и секреты (R56–R60)

`setup.py`: спрашивает `API_ID`/`API_HASH`/токен бота построчно, объясняет,
где их взять (my.telegram.org, @BotFather — R57), пишет `.env`, запускает
Telethon-логин с вводом кода и 2FA **в терминале самого скрипта** (R58), при
неверном коде/пароле — понятная ошибка и повтор, не падение (R56.1), в конце
проверяет: userbot жив (`get_me`), бот отвечает, указанный владельцем
Telegram ID совпадает с тем, что ввёл. Владелец записывается в `.env` как
`OWNER_ID` — панель на каждое входящее действие сверяет `from_user.id` с ним,
иначе «Доступ запрещён» + запись в `hits`-независимый лог попыток (R59).
Секреты нигде не запрашиваются и не сохраняются агентом сборки (R60) — только
именами в `.env.example`. `.env`, `./data/` и `*.session` — в `.gitignore` до
первого коммита (R60); `.env` добавлен туда уже в Phase 0 автопилота, `./data/`
и `*.session` добавляет первый тикет, который создаёт эту папку.

### 9. Устойчивость и автозапуск (R63–R65)

`FloodWaitError` — см. §5. Смерть сессии — обёртка вокруг вызовов userbot
ловит `AuthKeyUnregistered`/`SessionRevoked` и подобные, шлёт уведомление,
выставляет `settings.monitoring_paused_reason = "session_dead"`, пока не
пройдёт повторный `setup`-логин (R64). Docker: `restart: unless-stopped` на
оба сервиса. Без Docker — задача Планировщика Windows «при входе в систему»,
запускающая оба процесса (R65).

### 10. Ретеншн (R68)

Ежедневная задача (внутри `worker`) удаляет `hits` старше
`settings.retention_days` (по умолчанию 90); `delivery_queue` чистится вместе
со своим `hit_id`.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `matcher` | компиляцию ключей, правило совпадения | `compile(keywords, stopwords) -> Ruleset`; `Ruleset.match(text) -> MatchResult{matched, hit_keywords, blocked_by}` | regex-кэш, нормализацию регистра/ё-е, границы слов |
| `store` | схему SQLite, все таблицы §2 | по репозиторию на сущность: `sources`, `receivers`, `keywords`, `hits`, `delivery_queue`, `settings` — типовые `add/remove/list/get/update` на каждый | SQL, миграции, соединение с БД |
| `userbot` | сессию Telethon, обработку входящих/правок, исполнение доставки | `list_dialogs()`, `catch_up(chat_id, limit_days, limit_msgs)`, `deliver(hit, receiver) -> DeliveryResult` | Telethon-клиент, форвард/копия как деталь `deliver` |
| `panel` | UI-состояние (FSM), тексты и клавиатуры | ничего наружу — конечная точка; вызывает `store` и `userbot.list_dialogs/catch_up` | роутеры и клавиатуры aiogram |
| `worker` | цикл очереди, глобальный рейт-лимит, ретраи | `run()` (фоновый цикл) | таймеры бэкоффа, счётчик отправок в минуту |

Швы для тестов — те же публичные функции, без моков внутренностей:

- `matcher.Ruleset.match` — весь §3 (R17–R21) проверяется здесь, без Telegram и без БД.
- `store`-репозитории — дедуп (R32/R33), ретеншн (R68), очередь (R43/R61) проверяются на реальной (временной) SQLite, без сети.
- `userbot.deliver` — форвард/копия/карточка (R27–R31) проверяется с фейковым Telethon-клиентом за тем же интерфейсом.

Три шва, не один — `matcher` и `store` живут без Telegram вовсе, и держать их
за одним швом с `userbot` означало бы гонять сеть ради проверки регулярки.

## Подразумеваемые требования (R##i)

Четыре пункта ниже прямыми словами в брифе не названы — это разбор брифа «в
глубину» при **strict**: только то, без чего явно описанное рядом требование
не может работать однозначно, без новой возможности сверх заказанного.

- **R76i** — брифом описано поведение при недоступности *приёмника* (R43:
  уведомление, доставка в остальные продолжается). Источник — тот же тип
  сбоя (кикнули, чат удалён), и без симметричного решения поведение
  undefined; недоступный источник ведёт себя как недоступный приёмник.
- **R78i** — брифом описан вопрос о догоне только при снятии *глобальной*
  паузы (R53). У индивидуальной паузы источника (R41) свой ответ на тот же
  вопрос: без него неопределено, теряются ли пропущенные сообщения — решение
  переиспользует то же хранимое «последнее обработанное сообщение» (R35).
- **R79i** — брифом задано однокликовое удаление кнопкой (❌, R41/R46) без
  упоминания подтверждения; решение — оставить как описано, без
  дополнительного диалога.
- **R77i** — рассмотрен и **отклонён**, см. «Вне рамок»: команда `/export`
  (R55) сама по себе не подразумевает `/import`, добавлять его — это уже
  новая возможность, которую strict запрещает.

## Открытые места

Нет заглушек: спецификация не требует фактов о пользователе (цен, текстов,
брендинга), которые нельзя было бы получить из брифа или ввести в мастере
`setup`. Секреты (`API_ID`, `API_HASH`, `BOT_TOKEN`, `OWNER_ID`) — не
заглушки кода, а обычный ввод при первом запуске; их имена без значений уже
в `.env.example`.
