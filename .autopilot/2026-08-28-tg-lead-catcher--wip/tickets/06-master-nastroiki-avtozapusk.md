## Что должно заработать

Интерактивный скрипт `setup.py`, отдельная точка входа (не часть рантайма):
по шагам спрашивает `API_ID`/`API_HASH` (объясняя, что это my.telegram.org) и
токен бота (объясняя про @BotFather), сам пишет `.env`, запускает вход userbot
в Telethon — код подтверждения и 2FA-пароль вводятся **только в терминале
самого мастера**, никогда через бота; неверный код/пароль — понятная ошибка и
повторный запрос, без падения скрипта. Просит Telegram ID владельца (или
подсказывает, как его узнать) и записывает как `OWNER_ID` в `.env` — тот же
`OWNER_ID`, который проверяет `panel/auth.py` из тикета 04. В конце — проверка
живости: userbot залогинен (`get_me`), бот отвечает, доступ владельца работает;
печатает результат в духе «userbot подключён как …, бот @… жив, доступ у ID …».

`docker-compose.yml` поднимает `userbot` и `panel` с `restart: unless-stopped`
и общим volume под `./data/`. Для локального запуска без Docker — инструкция
и скрипт/XML для задачи Планировщика Windows «при входе в систему», запускающей
оба процесса.

## Критерии приёмки

- [ ] Скрипт объясняет, где взять `API_ID`/`API_HASH` и токен бота, до того как их запросить
- [ ] `.env` создаётся мастером со всеми нужными именами заполненными (кроме тех, что пользователь пропустил намеренно)
- [ ] Ввод неверного кода подтверждения даёт понятную ошибку и новый запрос, не завершает скрипт аварийно
- [ ] Ввод неверного 2FA-пароля — то же самое
- [ ] Код и 2FA нигде не отправляются через Bot API — только `input()`/эквивалент в терминале
- [ ] Финальная проверка печатает три факта: userbot подключён (с именем), бот жив (с username), доступ владельца подтверждён (с ID)
- [ ] `docker compose up` поднимает оба сервиса с `restart: unless-stopped` и общим `./data/`
- [ ] Инструкция для Планировщика Windows описывает создание задачи «при входе в систему», без ручных доработок кода
