## Что должно заработать

Два независимых, тестируемых без сети и без Telegram модуля:

1. `matcher` — компилирует список ключей и минус-слов в правило и умеет
   сказать про любой текст: сработало ли, по каким ключам, и не заблокировано
   ли минус-словом.
2. `store` — держит всю схему SQLite и репозитории для источников, приёмников,
   ключей, настроек, срабатываний и очереди доставки, включая обе дедуп-проверки.

Плюс каркас репозитория: зависимости, `.env.example` с именами (без значений)
`API_ID`, `API_HASH`, `BOT_TOKEN`, `OWNER_ID`, `TZ`, и `.gitignore`, дополненный
записями `./data/` и `*.session` (запись `.env` в `.gitignore` уже есть из
Phase 0 автопилота — не удалять и не дублировать).

## Из брифа, дословно

> «Один пользователь. Мультиарендности нет.»
> «Стек: Python, Telethon + aiogram 3 + SQLite.»
> «Язык интерфейса: русский. Таймзона Europe/Moscow, настраивается в .env.»
> «Плоская схема: один список источников, один набор ключей и минус-слов, один список приёмников.»
> «слово... совпадает с началом слова по границе слова: ловит «ремонт», «ремонта», «ремонтом», «ремонтник»; не ловит внутри слова («авто» не ловит «автора»)»
> «"ищу подрядчика"... точная фраза... несколько слов подряд»
> «re:\d{3}-\d{2}... regex... валидируется при добавлении; кривой regex отклоняется с понятной ошибкой и не роняет бота»
> «Регистр игнорируется, «ё» и «е» эквивалентны.»
> «Минус-слова — отдельный список с тем же синтаксисом. Совпадение минус-слова отменяет срабатывание («ремонт» + «вакансия» → не пересылать).»
> «Дедуп по сообщению (chat_id + message_id) — всегда, без отключения.»
> «Дедуп по автору и тексту: если тот же автор с тем же нормализованным текстом уже прилетал за последние 7 дней — второй раз не слать... Окно настраивается в UI, дедуп можно выключить.»
> «Секреты нигде не запрашиваются агентом и не сохраняются в репозиторий. .env, ./data/ и *.session — в .gitignore до первого коммита.»
> «SQLite в ./data/bot.db, сессия userbot — ./data/*.session. Папка в .gitignore, бэкап = копия папки.»
> «В лог срабатываний пишем: chat_id, message_id, автор (id / username / имя), сработавшие ключи, хеш текста (для дедупа), время, и первые 500 символов текста»

## Критерии приёмки

- [ ] `Ruleset.match("ремонта")` для ключа `ремонт` → `matched=True`; `Ruleset.match("автора")` → `matched=False`
- [ ] Точная фраза `"ищу подрядчика"` ловит только точное сочетание, не по отдельным словам
- [ ] `re:\d{3}-\d{2}` ловит совпадение по regex; заведомо кривой regex (`re:(`) при добавлении отклоняется с текстом ошибки и не попадает в список ключей
- [ ] «Ремонт» / «ремонт» / «ещё» / «еще» дают одинаковый результат матчинга
- [ ] Минус-слово в тексте отменяет срабатывание, даже если ключ тоже совпал; `blocked_by` называет минус-слово
- [ ] Схема SQLite создаётся с нуля (миграция/`CREATE TABLE IF NOT EXISTS`), все шесть таблиц из `interfaces.md` существуют
- [ ] Повторная вставка `hits` с тем же `(source_chat_id, message_id)` отклоняется на уровне репозитория (дедуп по id)
- [ ] Репозиторий даёт метод «это дубль по автору+тексту за окно N дней» и учитывает `dedup_enabled=false`
- [ ] `.env.example` содержит имена `API_ID, API_HASH, BOT_TOKEN, OWNER_ID, TZ` без значений; `.gitignore` содержит `./data/` и `*.session` в дополнение к уже существующей записи `.env`
- [ ] Тесты на `matcher` и `store` проходят без сети и без реального Telegram-аккаунта
