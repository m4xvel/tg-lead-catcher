# 0004. Два вида дедупа: по id и по автору+тексту

## Контекст

Бриф требует двух разных гарантий: одно и то же сообщение никогда не
пересылается дважды (R32/R25.1, в том числе при повторной обработке editing-
события), и один и тот же лид (тот же автор с тем же текстом) в другом чате в
пределах окна не создаёт вторую карточку, а дополняет первую (R33).

## Решение

В `hits` — два независимых индекса: уникальный на
`(source_chat_id, message_id)` для точного дедупа сообщения, и обычный на
`(author_id, text_hash, created_at)` для дедупа «тот же автор и текст за
последние N дней» с возможностью отключить окно.

## Почему

Рассмотрен и отклонён вариант с единственным ключом дедупа по id сообщения:
не решает R33 в принципе — R33 именно про совпадение в *другом* сообщении/чате,
то есть по определению другой `message_id`.

Рассмотрен и отклонён вариант с нечётким сравнением текста (similarity/
расстояние Левенштейна) вместо хеша: бриф говорит про «тот же текст», а не
«похожий текст» — точный хеш проще, предсказуемее и не рискует ложно
склеивать разные лиды.

## Последствия

Дедуп по тексту ловит только точное совпадение хеша — опечатка или другая
формулировка того же вопроса не будет распознана как повтор, и это осознанно
принято, а не недоработка. Оба вида дедупа живут в одной таблице `hits`,
значит любое будущее изменение семантики одного (например, окна R33) требует
внимания к индексам, обслуживающим оба сразу.
