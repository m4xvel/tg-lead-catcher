# 0009. D04 — regex-ключи не проходят ё→е-нормализацию

## Контекст

План (исходная формулировка spec.md §3) предполагал единую для всех видов
ключей нормализацию перед компиляцией: нижний регистр и замену «ё» → «е»
(R20), включая ключи вида `regex` (`re:`).

## Решение

Ревью показало: применение `.lower()`/замены ё→е к сырому regex-паттерну
ломает синтаксис регулярного выражения — инвертирует классы символов
(`\D`→`\d`, `[A-Z]`→`[a-z]` и подобные). Исправлено: regex-ключ компилируется
как есть, с единственной поправкой — флагом `re.IGNORECASE`; ё/е-эквивалентность
для regex сознательно не гарантируется. spec.md §3 приведён в соответствие
фактическому поведению.

## Почему

Рассмотрен и отклонён вариант с избирательной нормализацией — лоуэркейсить и
заменять ё→е только «буквальные» символы паттерна, оставляя regex-синтаксис
нетронутым: ненадёжно, поскольку невозможно текстовым проходом достоверно
отличить синтаксис регулярного выражения от буквальных символов без полного
парсинга самого regex.

Рассмотрен и принят вариант переложить ё/е-эквивалентность на пользователя:
пользователь, которому это нужно, пишет `[ёе]` в своём паттерне сам —
дешевле и безопаснее, чем чинить нормализацию под все возможные regex-конструкции.

## Последствия

R20 (регистронезависимость + ё=е) гарантирован только для ключей `word` и
`phrase`, но не для `regex` — если пользователь добавит regex-ключ с буквой
«е», написания через «ё» он автоматически не поймает, и это ожидаемое,
задокументированное поведение, а не баг. Любая будущая доработка матчера
должна учитывать это расхождение между видами ключей.
