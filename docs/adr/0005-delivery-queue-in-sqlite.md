# 0005. Очередь доставки в SQLite между «нашли» и «переслали»

## Контекст

Бриф требует: ничего не теряется при сбое доставки, 3 попытки с растущей
задержкой (R61); при нескольких приёмниках недоступность одного не блокирует
доставку в остальные, и по упавшему приходит уведомление (R43); есть
глобальный лимит отправки в минуту (R62).

## Решение

Совпадение сначала пишется в `hits`, затем по одной записи в `delivery_queue`
на каждый активный приёмник; отдельный цикл (`worker`) читает очередь по
`status=pending`, доставляет с ретраями и глобальным рейт-лимитом.

## Почему

Рассмотрен и отклонён вариант с синхронной доставкой прямо в обработчике
сообщения (форвард сразу при совпадении, без промежуточного хранения): отказ
или FloodWait на одном приёмнике заблокировал бы обработку остальных
приёмников и вообще следующих сообщений, нарушая R43; при падении процесса
между «нашли» и «переслали» доставка терялась бы безвозвратно, нарушая R61.

Рассмотрен и отклонён вариант с внешним брокером сообщений (Redis/RabbitMQ):
добавляет отдельный сервис в развёртывание (docker compose / Планировщик
Windows, R11), которое иначе обходится одной SQLite (R10/R66) и не рассчитано
на нагрузку, где нужен отдельный брокер.

## Последствия

Доставка больше не мгновенна — она ограничена циклом опроса очереди `worker`,
а не событием совпадения. Таблица `delivery_queue` навсегда привязана к
жизненному циклу `hits` (ретеншн R68 обязан чистить обе вместе). Глобальный
лимит (R62) считается запросом к самой БД («сколько `status=sent` за последнюю
минуту»), а не распределённым лимитером — это работает только пока доставку
исполняет ровно один процесс (`userbot`/`worker`); при появлении второго
исполнителя лимит перестанет быть верным без переделки.
